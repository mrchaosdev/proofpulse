# 10 — Demo and submission

## Demo objective

In under two minutes, prove that ProofPulse turns differentiated Nansen data into
an answer that is faster to understand, harder to overstate, and easy to audit.

## One-sentence pitch

> ProofPulse separates observed flow direction, evidence confidence, and wallet
> coordination risk—then makes every AI sentence traceable to Nansen data.

## Demo story

Choose a token fixture/live sample where evidence is genuinely interesting:

- price or activity is moving;
- at least two high-trust cohorts agree;
- at least one cohort contradicts them; and
- one top actor has useful related-wallet evidence.

Do not select or edit data to manufacture a predetermined bullish conclusion.
The story should demonstrate judgment under mixed evidence.

## 100-second storyboard

| Time | Screen/action | Narration goal |
| ---: | --- | --- |
| `0–10s` | Landing hero | Traders see movement before they understand who caused it |
| `10–20s` | Paste address, choose chain/timeframe | One investigation replaces several disconnected tabs |
| `20–35s` | Scores appear | Direction is separate from evidence quality and coordination |
| `35–52s` | Cohort flows | Nansen shows which cohorts accumulate and which contradict |
| `52–68s` | Buyers/sellers → inspect one actor | Move from aggregate signal to an accountable wallet trail |
| `68–80s` | Relationship graph/table | Concentration and relationships raise a risk, not an accusation |
| `80–92s` | Brief evidence links | Every model-assisted sentence points back to evidence |
| `92–100s` | Method/source/CTA | Built on Nansen; transparent method; public working product |

## Presenter rules

- Name Nansen capabilities while they are visible, not only in credits.
- State that Direction is observed flow, not prediction.
- Show one contradicting piece of evidence.
- Open one evidence ID so traceability is undeniable.
- Show the relationship table alternative briefly if the graph is used.
- Do not claim market-beating returns, manipulation detection, or ownership.
- If using fixture mode, say so immediately and keep its banner visible.

## Demo reliability plan

### Primary path

- Production URL in live mode.
- One prevalidated token/chain/timeframe.
- Cache warmed once within allowed product behavior.
- Model brief already cacheable from the evidence hash, while still labeled with
  its collection time.

### Fallback path

- Same production app in timestamped fixture mode.
- Same UI, normalizers, scores, and brief validation.
- No local dev server dependency.
- Video recording available locally and in a private backup location.

### Failure ladder

1. Retry only the failed source once if the UI says it is safe.
2. Continue the partial investigation and use it to demonstrate honesty.
3. Open the timestamped fixture through the visible fallback control.
4. Use the prerecorded video only if the deployed application is unavailable.

## Public README requirements

- Product name and one-sentence proposition.
- 15–30 second GIF or screenshot sequence.
- Problem, solution, and why Nansen is essential.
- Live demo URL.
- Architecture diagram.
- Exact Nansen capabilities used.
- Transparent score summary and link to methodology.
- Local setup with `.env.example`.
- Test commands.
- Security and product limitations.
- Fixture-mode explanation.
- Buildathon attribution and team credits.
- License/usage status.

## Submission package

- Public GitHub repository at the submitted commit.
- Working production URL accessible without organizer credentials.
- 90–120 second demo video with captions.
- Five-to-seven-slide deck.
- Short written description.
- Architecture image.
- At least three high-quality screenshots.
- Team member names/handles as permitted.
- List of Nansen endpoints/capabilities.
- Confirmation of original work and third-party asset licenses.
- Saved submission confirmation.

## Deck outline

1. **Problem:** a token move is visible before its cause is understood.
2. **Product:** investigate once; separate Direction, Confidence, and Coordination.
3. **Nansen advantage:** cohort flows, actor activity, relationships, performance.
4. **Demo:** one annotated investigation.
5. **Trust architecture:** evidence IDs, deterministic scoring, validated brief.
6. **Impact and next step:** alerts/comparison after the evidence core is proven.

## Screenshot list

- Investigation overview with all three outputs.
- Cohort flow panel with supporting and contradicting evidence.
- Wallet graph and table alternative.
- Evidence ledger expanded to one derivation.
- Mobile investigation state.

Never include API keys, provider dashboards, personal browser tabs, hidden wallet
identity, or unredacted terminal output.

## Post-submission

- Tag the submitted commit without changing history.
- Keep the production demo stable until judging finishes.
- Avoid formula/data changes unless fixing a critical error; disclose any such
  change clearly.
- Prepare a three-minute extended walkthrough and answers for data freshness,
  credit cost, hallucination prevention, and relationship semantics.
